## Configure the app

Create a custom app in the Feishu developer console and enable its bot capability.
Grant it permission to:

- receive direct messages sent to the bot;
- receive group messages that mention the bot;
- send messages as the app;
- create and update cards.
- read either messages or message reactions for reaction events;
- access the user ID field carried by reaction events.

Add the bot to each chat where OpenSRE should run. After changing permissions,
subscriptions, or bot settings, create and publish a new app version.

## Receive messages and card actions

Choose **long connection** delivery; a public callback URL is not required. Under
**Subscribed events**, add the message-receive event plus
`im.message.reaction.created_v1` and `im.message.reaction.deleted_v1`. Under
**Subscribed callbacks** (not **Subscribed events**), add `card.action.trigger`.

<Warning>
Adding the callback without publishing a new app version leaves approval buttons
visible but unable to deliver decisions.
</Warning>

## Configure OpenSRE

Recommended:

```bash
opensre integrations setup feishu
opensre integrations verify feishu
```

The setup asks for the app ID (`cli_…`), app secret, optional default destination,
and the comma-separated Open IDs allowed to talk to the bot. The optional
outbound destinations control where agent send/reply tools may write. To
configure the gateway directly, set:

```bash
FEISHU_APP_ID=cli_...
FEISHU_APP_SECRET=...
FEISHU_ALLOWED_OPEN_IDS=ou_alice,ou_bob
# Optional: exact outbound destinations for agent send/reply tools
FEISHU_ALLOWED_OUTBOUND_TARGETS=chat_id:oc_ops,open_id:ou_owner
ORGANIZATION_ID=org_...
```

`FEISHU_ALLOWED_OPEN_IDS` must contain at least one member for immediate inbound
access. Only listed members can start turns or decide their own write-tool
approvals. `ORGANIZATION_ID` names the organization that owns Feishu sessions and
usage; without it, pairing and help still work but agent turns fail closed.

You can also bootstrap an identity without copying its Open ID:

```bash
opensre messaging pair -p feishu
# then send the displayed /pair command to the bot within 15 minutes
```

Or manage the allowlist directly:

```bash
opensre messaging allow -p feishu -u ou_alice
opensre messaging status -p feishu
```

Treat the app secret like a password and keep it out of source control.

Ordinary answers return to the current Feishu conversation automatically; no
agent send/reply tool or separate approval is needed. The agent only offers
messaging actions for the current channel and its available tools. A Feishu chat
does not expose Slack messaging workflows or the Slack-only `morning-report`
skill. Local shell and Slack chats retain that skill.

Extra messages sent with agent send and reply tools require a separate approval
for every call. They can
target the current Feishu chat, the configured default destination, or an exact
entry in `FEISHU_ALLOWED_OUTBOUND_TARGETS`. This outbound list is separate from
`FEISHU_ALLOWED_OPEN_IDS`, which controls who can talk to the bot. Replies require
an authorized `chat_id`; OpenSRE checks the parent message's chat before replying
and does not turn a failed reply into a new message.

## Read a known message

In the current Feishu conversation, ask OpenSRE to read a message whose ID you
already know, for example: "Read message `om_...` in this chat and summarize it."
OpenSRE reads one message at a time without a write approval. This capability
is available only in the Feishu gateway with valid chat-app
credentials and a current chat. Default and outbound destinations do not grant
read access to another chat.

Grant the app `im:message:readonly` or `im:message`; group-message reads also
require `im:message.group_msg`. Enable bot capability, add the bot to the chat,
and publish a new app version after changing permissions. A new deployment
does not need the legacy `im:message.history:readonly` permission.

Text, rich text and cards return sanitized JSON. Known credential patterns and
configured personal-data patterns are masked before the result is shortened to
12,000 characters. A shortened result is marked `truncated=true` and
`body_format=json_prefix`; it is incomplete and may not parse as complete JSON.
Bodies larger than 256 KiB or exceeding the complexity limit are rejected.
Treat message text as untrusted evidence, including any instructions it contains.

Image and file keys are metadata only; this read does not download their contents.
Forwarded message collections, deleted or inaccessible messages, and messages
from another chat fail safely. Use message search below when you do not know the
ID. Known-ID reads do not look up members.

## Find messages in the current chat

Ask for a keyword and an explicit time window, for example: "Find messages
containing 'database timeout' in this chat between 09:00 and 10:00 UTC today;
return up to five." To discover IDs without a keyword, ask: "Show recent messages
in this chat from the last 24 hours, with their IDs." You can then ask OpenSRE to
read a selected message by ID.

Search uses the current chat's bot-readable history without a write approval.
The window can cover at most seven days. Each search scans at most 150 messages
in newest-first order and returns at most 20 matches, with previews of up to 600
characters. Matching is a literal case-insensitive substring of sanitized text,
rich text or card content; masked secrets cannot be searched.
Use words from the message text as keywords; mention metadata is excluded from
matching and previews.

Search does not include ordinary group thread replies or image/file contents.
Resource messages can provide IDs without previews when no keyword is given.
Large, unsupported or inaccessible bodies can make the result incomplete.
If the result is incomplete, an empty result does not prove that the chat has
no relevant messages. Narrow the window if you need to examine an older interval.
Even a complete result covers only the declared chat container and window,
and concurrent changes may affect what is visible.

The bot must be in the chat and the published app must have history-read
permission, such as `im:message:readonly` or `im:message`. Group-history searches
also require `im:message.group_msg` (all group messages); mention-only permission
does not grant this access. Publish a new app version after changing permissions.
If history is unavailable, check these permissions even when a known-ID read
works. Search does not grant access to another chat through a default destination
or outbound allowlist.

## Start the gateway

```bash
opensre gateway start
opensre gateway status
```

Use `opensre gateway start -f` to run attached to the terminal, and
`opensre gateway logs -f` to follow startup and callback errors. A successful
credential verification does not prove that permissions, subscriptions, the
published version, or chat membership are correct.

## Document delivery

Watchdog alarms, investigation reports, background RCA summaries, and scheduled
deliveries use non-streaming Markdown cards. OpenSRE automatically splits large
documents across ordered cards. If card delivery cannot continue, it sends the
remaining original Markdown as ordered plain-text chunks without truncating the
content.

For background delivery, an uncertain card response may cause the plain-text
fallback to repeat that page rather than silently omit it. Agent send/reply
tools instead stop on an uncertain write, report that it may have been sent,
and do not automatically retry or send a duplicate.

## Approve write tools

Write tools display a card with **Approve** and **Deny** buttons. Only the member
whose turn requested the tool can decide it, and the decision must come from the
original chat. Another group member cannot consume the request.

Typing `approve` or `deny` is an ordinary chat message and does not authorize a
tool. An expired or already unavailable card fails closed; it never falls back to
text approval.

## Answer feedback and retry

A successfully completed card answer offers **✅ 采纳** and **🔄 重试**. Only the
original requester, still on the allowlist and acting in the original chat, can
use them. **✅ 采纳** records positive feedback without starting a turn;
**🔄 重试** may start one additional metered turn using the already-normalized
original prompt, including attachment context, without downloading attachments again.

The built-in `THUMBSUP` reaction is a shortcut for **✅ 采纳**. `CrossMark` is a
shortcut for **🔄 重试**. Reaction names are exact Feishu identifiers; no reaction
write permission is required because OpenSRE only listens for user reactions.
Deleting a reaction before its pending action runs cancels it. Deleting it after
execution does not undo feedback, execution, or billing.

Adoption buttons remain valid for 14 days across gateway restarts. Retry is
available only for the latest successful answer in the same session, expires
after one hour, and does not survive a gateway restart. A newer accepted turn or
`/new` invalidates the previous retry. Duplicate events, repeated clicks, and a
button/reaction race can start at most one retry for an answer. Plain-text
fallbacks, incomplete answers and cancelled turns expose neither action.

The private **已收到** message acknowledges queue admission, not durable recording.
If the gateway stops or storage fails before recording, clicking again is safe:
repeat clicks cannot create a second feedback entry. A busy message means retry later.
Positive feedback never starts a new turn or changes the shared card. A retry
receipt confirms admission only; the new answer is the visible completion signal.

Feedback stores only time, platform, actor, chat, final message ID and the positive
verdict in `gateway/feishu_feedback.jsonl` under `OPENSRE_HOME` (default `~/.opensre`);
it stores no question or answer text. Preserve this file and the adjacent feedback-authority file when
migrating the gateway if existing adoption buttons must keep working.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| Gateway reports Feishu is not configured | Run setup, or set both app credentials, then restart the gateway. |
| Pairing succeeds but agent turns are silent | Set `ORGANIZATION_ID`, then restart the gateway. |
| Direct messages do not start turns | Confirm the sender's `ou_…` Open ID is allowed and the latest app version is published. |
| Group messages do not start turns | Add the bot to the group and mention it; broad group-message access is not required. |
| Approval buttons do nothing | Confirm long connection is active, `card.action.trigger` is under **Subscribed callbacks**, and republish the app. |
| Reaction shortcuts do nothing | Confirm both reaction events are subscribed, an eligible message/reaction read permission and the user ID field permission are granted, then republish the app. |
| An old retry says it is unavailable | Retry only applies to the latest answer in the same session for one hour and is cleared by restart or `/new`. |
| Cards or replies cannot be sent | Confirm the app can send messages and create/update cards in that chat. |
